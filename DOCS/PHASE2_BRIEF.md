## 1. Where Phase 1 landed

- **Database** — all Phase 1 tables in `0001_phase1_schema.sql`: Users, Parents, Teachers, Students, Student_Parents, Instruments, Grades, Enrolments, Lesson_Templates, Template_Enrolments, Pricing. The `resolve_price()` SQL function is already in place for Phase 3 invoice work.

- **RLS** — full permissions matrix from SPEC.md §8 enforced in `0002_phase1_rls.sql`. Six helper functions (`is_admin`, `is_teacher_for_student`, `is_teacher_for_template`, `is_parent_of_student`, `is_self_student`, `is_teacher_for_enrolment`) are available for Phase 2 policies to build on.

**What Phase 1 deliberately left out** (deferred to Phase 2/3): `Lesson_Instances`, `Attendance`, `Invoices`, `Invoice_Line_Items`, `Reminders`, background jobs, WhatsApp delivery, PDF generation.

## 2. Decisions resolved before Phase 2

These were open or ambiguous in the spec; all are now settled:

| # | Decision | Resolution |
|---|---|---|
| C1 | Parent identity model | **Option A** — parents have no separate login. The student's credentials are the single family login. Parent contact details live on the `Parents` record (no `user_id` FK). See `DOCS/ADR/ADR-001-parent-identity-model.md`. |
| C2 | Push token collision | Resolved by C1: one push token per family (student's device). WhatsApp is the out-of-band channel for parents. |
| C3 | Ad-hoc attendee pricing | `CHECK` constraint in `attendance`: when `is_adhoc = true`, `override_price` must be set. App must prompt for a price when adding an ad-hoc student. |
| C4 | Academic calendar | `calendar_days` table added in `0003_phase2_schema.sql`. Instance-generation worker must call `is_school_open(date)` before creating each instance. |
| I5 | Auth mechanism | Email + password for students, teachers, and admins. Parents have no login. |
| I6 | Users ↔ auth.users | `Users.id` = `auth.users.id`; mirrored via trigger. |
| I7 | Soft-delete policy | `is_active` flags; no hard deletes on entities referenced by historical records. |

## 3. What was added for Phase 2

Two new migration files are ready to apply:

### `0003_phase2_schema.sql`
- **`calendar_days`** — school closures, term breaks, exam weeks. Admin-managed. The `is_school_open(date)` function checks it.
- **`lesson_instances`** — one row per actual lesson occurrence. Supports both template-backed instances (generated by the worker) and one-off/makeup lessons (`is_one_off = true`, `template_id = null`). Includes a `UNIQUE(template_id, date)` constraint to prevent duplicate generation.
- **`attendance`** — one row per student per instance. Captures present/absent/late, ad-hoc flag, and fee override fields. `CHECK` constraint enforces that ad-hoc rows have `override_price` set (C3 resolution).
- **`effective_capacity(instance_id)`** helper — returns `capacity_override` if set, else `max_capacity` from the template.
- **`instance_headcount(instance_id)`** helper — returns current non-absent headcount; use for capacity warnings in the UI (I3).

### `0004_phase2_rls.sql`
- Two new helper functions: `is_teacher_for_instance()` and `is_student_or_parent_for_instance()`.
- RLS enabled on `calendar_days`, `lesson_instances`, `attendance`.
- Permissions align with SPEC.md §8: teachers can insert + update attendance for their own instances; only admins can delete; enrolled students and their parents can read upcoming instances before attendance is marked.

## 4. Phase 2 feature scope

Directly from SPEC.md §9 Phase 2:

| Feature | Key behaviours | Tables touched |
|---|---|---|
| Lesson instance generation | Worker generates instances 8 weeks ahead from active templates; skips `calendar_days`; one instance per template per date | `lesson_instances`, `calendar_days` |
| Attendance marking | Teacher marks each student present / absent / late; admin can do the same for any instance | `attendance` |
| Ad-hoc student add | Teacher adds a student not on the template; `is_adhoc = true`; must set `override_price` | `attendance` |
| Fee override | Teacher or admin sets `override_price` + `override_reason` on any attendance row they own | `attendance` |
| Lesson cancellation | Teacher or admin sets `status = cancelled` + `cancelled_reason` on an instance | `lesson_instances` |
| One-off lesson creation | Admin creates a `lesson_instances` row with `is_one_off = true` and no `template_id` | `lesson_instances` |
| Push notification reminders | 12 hours before each lesson; sent to teachers, students, and primary parents | `lesson_instances`, `Reminders` (Phase 3 table — see §5 below) |

## 5. Suggested build order

Work through these stories roughly in order — each unlocks the next:

1. **Apply migrations** — `supabase db reset` locally (or `supabase db push` for hosted) to apply `0003` and `0004`. Then regenerate TypeScript types.

2. **Phase 1 CRUD screens** (prerequisite) — Admin: create/edit students, link parents, manage enrolments, create lesson templates, assign students to templates. Without data in the DB, there's nothing to generate instances from.

3. **Instance generation worker** — A Supabase Edge Function (cron-triggered) that:
   - For each active `lesson_templates` row
   - For each date in the next 8 weeks where `day_of_week` matches
   - If `is_school_open(date)` is true
   - Inserts a `lesson_instances` row (on-conflict do nothing for idempotency)

4. **Attendance marking screen (teacher)** — List today's lesson instances for the logged-in teacher. For each: list enrolled students, mark present/absent/late. Save each row to `attendance`. Include a fee-override toggle.

5. **Ad-hoc student add** — In the attendance screen, let the teacher search for any active student not already on the instance. On add: prompt for `override_price` (required), set `is_adhoc = true`.

6. **Lesson cancellation** — Teacher (or admin) can cancel an instance from the schedule view. Prompts for `cancelled_reason`. Sets `status = 'cancelled'` on the instance row.

7. **One-off lesson creation (admin)** — Admin screen to create a standalone `lesson_instances` row. Fields: teacher, instrument, type, date, start time, duration, room. No template required.

8. **Schedule views (student / parent / teacher)** — Read-only upcoming lesson list. Students and parents see their own lessons; teachers see their full timetable.

9. **Push notification reminders** — Requires `Reminders` table (Phase 3 schema). But Expo + Firebase setup (app.json config, `expo-notifications` install) can be done now so it's ready when the table lands. Reminder dispatch worker creates `Reminders` rows; a second worker sends and updates `sent_at`.

## 6. Risks and watch-outs

**Instance generation idempotency** — The worker must use `INSERT … ON CONFLICT (template_id, date) DO NOTHING` to be safe to re-run. The `UNIQUE(template_id, date)` constraint in the schema enforces this.

**DST and reminders (I10)** — `Lesson_Templates.start_time` has no time zone. When computing the "12 hours before" reminder timestamp, convert to `Europe/London` using `AT TIME ZONE 'Europe/London'` in SQL or a JS `Intl` object. If ignored, reminders will fire an hour early or late twice a year.

**Capacity enforcement (I3)** — The schema provides `effective_capacity()` and `instance_headcount()` helpers but no hard DB constraint (a hard constraint would block legitimate admin overrides). The UI should call both helpers before allowing an ad-hoc add and show a warning when headcount would exceed capacity. An admin-only "override capacity" confirmation is enough.

**Schema corrective migration** — The Phase 1 schema has `parents.user_id` and a `parent` enum value in `user_role`, both artifacts of the Option B assumption. A migration (`0005_fix_parent_identity.sql`) is needed to drop `parents.user_id` and clean up the associated RLS policies before Phase 2 screens are built. The `AppStack.tsx` parent routing case should also be removed or merged into the student case.

**TypeScript types** — Phase 1 shipped with a hand-written `src/lib/types.ts` covering only Phase 1 tables. After applying migrations `0003` and `0004`, regenerate the full type file:
```bash
supabase gen types typescript --local > src/lib/database.types.ts
```
Delete `src/lib/types.ts` once the import references are updated.

**Missing CI** — No lint, typecheck, or migration-lint CI exists yet. Before Phase 2 screens land, add at minimum:
```
tsc --noEmit
supabase db lint
```
as a GitHub Actions job on every PR.
